## 盘中快照改为"每 10 分钟一次"单帧模式（用户要求）

### 需求
"盘中的定时快照任务 间隔保证10分钟一次，收盘后的全量更新保持不变"。

### 根因
旧模型是"会话模型"：`INTRADAY_SESSION_BY_CRON` 把 `09:30/13:00` 等少数 cron 映射成 morning/afternoon 会话，会话启动后内部每 600s 抓一帧直到 `SESSION_END_EPOCH`。依赖单个启动 cron 准时——GitHub 高峰拥堵常把早盘 cron 延迟到午后，此时 `current>end(11:30)`→`session_finished`→整段上午缺失（即 07-24 零运行的主因）。

### 改动
1. `daily_review/application/workflow_schedule.py`
   - 新增 `INTRADAY_ONCE_BY_CRON`（26 个 cron：上午 09:30-11:30、下午 13:00-15:00，每 10 分钟一个，北京时间）→ 各自 `mode="once"`。
   - `INTRADAY_SESSION_WINDOWS` 下午窗口由 (14,50) 延到 (15,0)。
   - `resolve_intraday_session` 优先识别 once cron 返回 `mode="once"`（before/after 窗口 skip）。
2. `.github/workflows/intraday_runtime.yml`
   - schedule 6 个错峰 cron → 26 个 10 分钟 cron。
   - concurrency 由 morning/afternoon 双组 → 单一 `intraday-runtime-once`（串行，避免并行 push 互相覆盖丢帧；单次 ~1-3min < 10min 间隔不会级联）。
   - `publish_pages.yml` 未改动（收盘全量更新保持不变）。

### 验证
- YAML 合法（26 cron，workflow_dispatch 保留，并发组为 intraday-runtime-once）。
- 单测：26/26 cron 自身时刻 `mode=once,skip=False`；09:30/11:30/13:00/15:00 边界命中；15:01 与延迟到午休的 cron 正确 `session_finished` skip。
- 代价：交易日 ~26 runs/日（≈1100 min/月，免费私有仓 2000min 内）；gh-pages 每日 ~26 次提交。漏一个 cron 仅丢该 10min 槽位，相邻补上——满足"保证 10 分钟一帧"。

## 二次拉快照（17:27 周日）发现 API 周末时效性

- 上午 ~14:45 跑：`simulated=False`、health=valid、三池 valid、有 latest 真实指标（07-24 残留快照有效）。
- 傍晚 ~17:27 再跑：同回退 07-24，但 `simulated=False`、`health=stale`、`count=0`、`pool_status=null`、`latest` 空。
- **结论**：必盈 API 对"上一交易日实时快照"的保留**有时效**——周末上午尚可命中有效残留，到傍晚即被标记 stale 返回空壳。休市越久越易 stale。
- 含义：① 休市日"模拟快照"只能验证**管线连通性**，不能保证有数据；② 真·有数据的 live 切片必须交易日 09:30-15:00 跑；③ 若 intraday 定时任务在长假/周末空跑，会持续写 stale 空壳——前端需对 `health=stale` 做明显提示而非显示空白。
- 注：本次 stale 判定来自 API 返回，非本地逻辑 bug；watch_runtime 仍按预期工作（exit 0、文���正常写入）。
- **复盘验证**：用户显式指定 `./qr.sh watch-slice 2026-07-24` 跑，结果与自动回退 07-24 完全一致（stale/空）。→ 排除"回退逻辑 bug"假设，确认根因是 API 周末对历史交易日实时快照的保留时效（傍晚即清）。有效实时数据只能在交易日 09:30-15:00 跑出。
